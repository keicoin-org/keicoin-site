# AGENTS.md — working on keicoin-site

> **This file is for an agent editing this repository.** It is not the published
> one. `keicoin.org/AGENTS.md` is generated by `src/site/machine.ts` into
> `dist/AGENTS.md` and is written for an agent *integrating the Kei SDK into
> somebody's game*. Editing this file changes nothing that is served; editing
> `machine.ts` does.

Read [`README.md`](README.md) first for the four rules and the layout. This file
is the procedure.

## Before you write a sentence on a page

Answer these. They are the questions that would have prevented every wrong claim
this site has published.

| Question | If the answer is no |
|---|---|
| Can a reader check this in one step, from the page saying it? | Add the command or the URL, or delete the claim. |
| Is it already stated somewhere else in `content.ts`? | Render the existing record. Do not write a second copy. |
| Does the page state the limit at the same volume as the capability? | It is not finished. |
| Is it true of what is **released**, rather than of a branch? | Say which branch, and say it is a draft. |

The load-bearing constraint: an agent reading this site cannot ask a follow-up
question and cannot discount enthusiasm. A claim that a human would read as
optimism is, to an agent, a specification — and then somebody's broken
integration.

## Where a change goes

- **A fact about the product** → `src/site/content.ts`. It reaches the landing
  page, the use-case pages, `/status`, `llms.txt` and `AGENTS.md` from there.
- **The status line on every page** → `SITE.milestone` and `SITE.status` in
  `src/site/layout.ts`. One place, because it appears everywhere.
- **The four tracks** → the `TRACKS` record in `content.ts`. The landing page,
  `/status` and `llms.txt` all render it; `src/site/claims.test.ts` asserts they
  all still do.
- **A guide, a reference page, or the writing about a demo** → `docs/`.
- **A new top-level page** → add a `Page` to `PAGES` in `content.ts`. `build.ts`
  writes it and the sitemap picks it up; there is no route table to update.

## Checks

```sh
bun install
bun test            # copy guards, clicker logic, demo artifact mapping
bun run typecheck
bun run build       # writes dist/, then VitePress builds docs/
bun run check       # the above, plus wrangler deploy --dry-run
```

Run `bun run check` before opening a pull request. Do not deploy: deployment is
a separate, deliberate act.

## The tests that will stop you, and why

Neither is stylistic. Both encode a claim that was wrong on the live site.

- **`src/site/claims.test.ts`** — no milestone numbers anywhere a reader sees
  them; the four tracks present on all three surfaces; every page carrying the
  no-mainnet, no-value status line; and the two drafts (Carpet Markets, Create
  Kei MMO) described as drafts in the machine-readable files.
- **`src/site/harness-docs.test.ts`** — every documented Create Kei MMO command
  is one the harness would actually accept. This page once printed
  `--source template --template button`, which the harness now refuses with a
  stable error code; a reader running it concludes the harness is broken rather
  than that the page is stale.

If one fails, fix the copy. Suppressing it republishes the claim it was written
to catch.

## What you may not do here

- Do not describe anything as mainnet-ready, launching, or awaiting a date.
  Mainnet is not a build task.
- Do not present Carpet Markets as an operable market, or Create Kei MMO as a
  tool that produces a working game. Both are named accurately in `README.md`.
- Do not restate the API on a page as if this site owned it. Link the package and
  `SPEC.md`; the site is never the source of truth for the API.
- Do not add a claim to `llms.txt` or `AGENTS.md` that is not also on a page. The
  whole point of generating them from `content.ts` is that the site cannot tell a
  human one thing and an agent another.
